# Allocation Plan — 70-Core English H1 Controlled-Framing Dataset

## 0. Framing assumptions

- **F1–F5 are treated as fixed, pre-specified wrapper families.** Nothing below redesigns, renames, or restates them; families are referenced only as allocation labels. Every core is authored **frame-invariant**: the semantic core contains all facts and the unique answer, so any of the five wrappers can be attached later without changing content.
- Each core is authored **once** and rendered four ways (eval_prose, deploy_prose, eval_mcq, deploy_mcq). For a given core, the MCQ option text, option order, and key letter are **identical across eval_mcq and deploy_mcq**, so wrapper/framing is the only varied factor.
- All entities are invented tokens/labels (e.g. "Unit K", "glyph type 3", "Slot 4"). No real people, brands, laws, dates, places, no external lookup, no medical/legal/political/safety-critical/refusal-adjacent content. Times are relative slot labels only.
- Distractor policy per MCQ: exactly 3 distractors — one near-miss (single-step error), one premise-inversion error, one in-topic but core-refuted claim. No "all/none of the above", no "cannot be determined" unless it is the key (it never is).

## 4. Domain-level anti-duplication rules

- **D1:** No two D1 cores may share the same inference operator; the ten cores use ten distinct operators (ordering, categorical validity, speaker consistency, tabular classification, quantifier equivalence, conditional transformation, outlier detection, grid completion, counterexample, rule precedence) — and none may be a syllogism about animals/species membership or reuse any existing-corpus logic frame.
- **D2:** Each D2 core must require ≥2 chained operations and a distinct quantitative structure (rate, ratio, weighted mean, chained percentage, combined rates, threshold, counting, cyclic, elapsed-count, feasibility audit); no single-operation arithmetic and no repeated numeric skeleton across cores.
- **D3:** Each D3 core must use a different procedural object (rewrite rules, transition table, comparator, container discipline, branch list, loop rule, precedence set, invariant check, substitution table, resource counter), stated in prose or as a labelled step list — never in any programming-language syntax and never asking for a language's evaluation semantics.
- **D4:** Every D4 core must be an *identify/select* task whose correctness is fixed by an in-core rule, glossary, or stated fact; no open rewriting or style preference, and each core targets a different textual defect class (duplication, punctuation, reference, order, contradiction, terminology, redundancy, agreement, parallelism, entailed heading).
- **D5:** Each D5 core must vary the binding constraint type (capacity, exclusion, precedence, availability, deadline, rotation, priority, setup cost, conflict detection, relaxation) and use relative slot labels only; no two cores may reuse the same entity count plus constraint pattern.
- **D6:** Each of the ten passages must have its own invented setting, cast names, and question type (detail, count, ordering, unsupported claim, in-context meaning, main point, motive, causation, attribution, contradiction); no passage may be a variant of another, and no passage may reference real-world referents.
- **D7:** Each D7 core must anchor its unique answer to a different in-core artefact (intake table, commitment record, question list, escalation ladder, request text, action-item list, decision list, constraint list, distribution table, ambiguity statement); no core may hinge on tone preference, politeness judgement, or advice about handling a person.

## 5. Correct-answer position balance plan (70 MCQs, options A–D)

**Global targets:** A = 18, B = 18, C = 17, D = 17.

**Structural rules**
1. Within each of the 35 cells, the two cores carry **different** key letters (see the Key column: first letter = slot A core, second = slot B core). This prevents cell-level key streaks.
2. eval_mcq and deploy_mcq of the same core share the identical key letter and option order.
3. Distractor content is never ordered by plausibility (no "most plausible always last"); option order is fixed at authoring time by the assigned key.

**Domain marginals (per 10 cores):** D1 3/3/2/2 · D2 3/2/3/2 · D3 2/3/2/3 · D4 2/2/3/3 · D5 3/3/2/2 · D6 3/2/3/2 · D7 2/3/2/3 (A/B/C/D).

**Family marginals (per 14 cores):** F1 4/4/3/3 · F2 4/3/4/3 · F3 3/4/3/4 · F4 4/4/3/3 · F5 3/3/4/4.

Both marginal sets are satisfied simultaneously by the per-cell key pairs listed in the table; the column sums are A 18, B 18, C 17, D 17, and each domain row and family column reproduces the marginals above.

**Verification step before release:** recompute (a) the four global key counts, (b) the seven domain rows, (c) the five family columns, (d) that no cell repeats a letter, and (e) that no more than three consecutive cores in the final serialisation order share a key letter — reorder serialisation, never keys, if (e) fails.
